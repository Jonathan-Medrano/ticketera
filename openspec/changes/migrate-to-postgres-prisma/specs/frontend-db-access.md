# Spec: Frontend Database Access

**Change:** migrate-to-postgres-prisma
**Capability:** Database access from the Next.js frontend (platea/)
**RFC 2119 keywords apply throughout.**

---

## Summary

The `platea/` Next.js app currently uses `mysql2` directly in two library files (`password-version.ts`, `route-rate-limit.ts`) and executes DDL at runtime. After migration, `platea/` MUST use the Prisma client exclusively. All runtime DDL is removed. The types generated by Prisma MUST be consistent between the backend and frontend.

---

## Background

Known `mysql2` and DDL usage in `platea/`:

| File | Issue |
|------|-------|
| `platea/lib/password-version.ts` | Executes `CREATE TABLE IF NOT EXISTS` + raw `mysql2` queries |
| `platea/lib/route-rate-limit.ts` | Executes `CREATE TABLE IF NOT EXISTS` + raw `mysql2` queries |

Both files MUST be refactored. The tables they create MUST move to `prisma/schema.prisma`.

---

## Requirements

### R1 — No mysql2 in frontend

- `platea/` MUST NOT import `mysql2` or `mysql2/promise` anywhere.
- All database queries in `platea/` MUST use the Prisma client.

### R2 — No runtime DDL in frontend

- `platea/lib/password-version.ts` MUST NOT execute any DDL.
- `platea/lib/route-rate-limit.ts` MUST NOT execute any DDL.
- The tables they currently create (`password_versions` or equivalent, rate limit table) MUST be declared in `prisma/schema.prisma` and created by `prisma migrate deploy`.

### R3 — Prisma client consistency

- `platea/` MUST use a Prisma client generated from the same `prisma/schema.prisma` as the backend.
- If `platea/` and `backend/` share a monorepo, they MAY share one `node_modules/@prisma/client` package.
- If they are separate deployments, each MUST generate the client from the same schema file (single source of truth). The generated types MUST be identical.
- Type drift between frontend and backend Prisma clients is NOT permitted.

### R4 — Connection strategy for frontend

- `platea/` server-side code (Server Components, Route Handlers, Server Actions) MUST connect to the database using the Prisma client.
- The connection string used by `platea/` MUST come from environment variables (`DATABASE_URL` and optionally `DIRECT_URL`).
- `platea/` SHOULD use the pooler connection (port 6543) for read queries and short transactions.
- `platea/` MUST use the direct connection (port 5432) if it needs to perform locking operations (currently none known in the frontend, but this is a forward-looking constraint).

### R5 — Rate-limit table access

- The rate-limit check in `route-rate-limit.ts` MUST be refactored to use Prisma client queries instead of raw SQL.
- The rate-limit table MUST have the same semantics as before: store request counts per key with a time window.
- The refactored implementation MUST NOT regress on security (rate limiting MUST still function correctly).

### R6 — Password version access

- The password version check in `password-version.ts` MUST be refactored to use Prisma client queries.
- The semantics MUST be preserved: ability to read, insert, and compare password version records per user.

## Scenarios

### Scenario 1 — SSR data access via Prisma

```
Given a Next.js Server Component that reads event data for the tenant storefront
  And the Prisma client is configured with DATABASE_URL
When the Server Component is rendered on the server
Then the Prisma client executes the query against Postgres
  And the component renders with the correct data
  And no mysql2 connection is opened
```

### Scenario 2 — Rate-limit lookup

```
Given a request to a rate-limited API route
  And the rate-limit table exists in Postgres (created by prisma migrate deploy)
When route-rate-limit.ts checks the request count for the caller's key
Then the check uses the Prisma client (no raw SQL driver)
  And if the limit is exceeded, the request is rejected with HTTP 429
  And no CREATE TABLE statement is executed during the request
```

### Scenario 3 — Password version check

```
Given a user login attempt
  And the password_versions table exists in Postgres (created by prisma migrate deploy)
When password-version.ts reads the user's password version
Then the read uses the Prisma client
  And the version is returned correctly
  And no CREATE TABLE statement is executed
```

### Scenario 4 — Frontend build with Prisma

```
Given the Prisma client has been generated (`prisma generate` run in postinstall)
When `npm run build` is executed in platea/
Then the build succeeds with no type errors related to Prisma
  And no mysql2 import is referenced in the build output
  And the generated client types are consistent with the backend
```

### Scenario 5 — Schema type consistency check

```
Given both backend/ and platea/ generate the Prisma client from the same schema.prisma
When a developer adds a new field to a model in schema.prisma and runs prisma generate
Then both backend/ and platea/ TypeScript compilation reflects the new field
  And a type error occurs in any code that tries to access a removed or renamed field
```

---

## Out of Scope

- The specific Prisma query syntax for rate limiting or password versioning (design/apply phases).
- Whether `platea/` and `backend/` share `node_modules` (design decision).
- Next.js middleware database access via Edge runtime (not currently used).
